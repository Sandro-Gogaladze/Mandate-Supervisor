# Phase 10 — Live multi-agent UI

Status: complete for the core loop (case queue → live run → results). `dashboard/` (React + Vite + Tailwind + shadcn/ui + React Flow + CopilotKit), `dashboard/server/copilot-runtime.js` (Node), `api/main.py` (FastAPI). Verified live end-to-end, including the escalation loop, in-browser.

## 1. Why the backend had to be rewritten first

CLAUDE.md's spec is specific: React Flow fed by the graph's own `get_graph()`, and CopilotKit/AG-UI driving a live step feed as nodes execute — not a static results page. That requires the graph to stream node-by-node while it runs, which means every agent call on the hot path has to be awaitable inside LangGraph's own event-streaming machinery (`astream_events`), which only instruments the async callback path.

Every reasoning module (`agents/llm.py`, `*_reasoning.py`, `pipeline/dispatch.py`) was on the raw, synchronous `anthropic` SDK through Phase 9. All of it — `get_client()`/`extract_tool_input()` → `get_model()`/`get_tool_call()`, backed by `langchain_anthropic.ChatAnthropic` — plus every `review()`/`run()` method and every graph node in `pipeline/graph.py` becoming `async def`. `pyproject.toml` gained `langchain-anthropic`, `langchain-core`, `ag-ui-langgraph[fastapi]`, `copilotkit`, `fastapi`, `uvicorn`; `anthropic` pinned to `>=0.96.0,<1.0.0` since no published `langchain-anthropic` yet supports `anthropic>=1.0.0`. `tests/fakes.py` centralizes one `FakeChatModel` (replacing five per-file fakes) — it took two wrong designs before landing on the right one: keying strictly by the bound tool name breaks the "wrong tool called" test, iterating over *all* configured responses breaks call-count assertions when a single fake stands in for a multi-call review. The fix binds per-call (`.bind()` returns a copy carrying just that call's tool name) while sharing `call_log` and `last_bind_kwargs`/`last_messages` across copies via a mutable `_state` dict, and returns an empty tool-call list (not a `KeyError`) when the bound tool isn't in the fake's configured responses.

All 113 pre-existing tests were ported to `async def` and pass unchanged in substance (`pytest-asyncio`, `asyncio_mode = "auto"`). This was the highest-risk part of the phase — a mechanical rewrite touching every agent — and it was done and verified (full live pipeline run via `run_case()`, multiple cases) before any UI code was written.

## 2. What the "thinking stream" actually is

Anthropic's adaptive thinking (`thinking={"type":"adaptive"}`, `output_config={"effort":"high"}`) was tried first as the literal chain-of-thought stream. Confirmed live: thinking content blocks come back **empty** except for a cryptographic signature — `{"thinking": "", "type": "thinking", "signature": "..."}`. There is no visible extended-thinking text to stream.

What *does* stream, continuously, is each tool call's arguments building up character-by-character as `input_json_delta` chunks — 556 `on_chat_model_stream` events in one traced run. Since every specialist's real output (`reason_about_case`, `record_observations`, `propose_dispatch_plan`, `record_log_analysis`, ...) is itself a tool call, watching those arguments assemble live *is* watching the model think — the `reasoning`/`explanation` fields fill in token-by-token in the UI's step feed exactly as the model writes them. This is the mechanism the whole live-feed design is built on, not a fallback.

## 3. Three tiers, and why there are three

- **`api/main.py`** (FastAPI) — `ag_ui_langgraph.add_langgraph_fastapi_endpoint()` wraps `pipeline/graph.py`'s compiled graph directly as a spec-compliant AG-UI SSE endpoint at `/agent`, plus plain REST (`/cases`, `/cases/{id}`, `/graph` — the last one generated from `_graph.get_graph()`, never hand-maintained, per CLAUDE.md). A `MemorySaver` checkpointer lives only here, matching CLAUDE.md's checkpointer philosophy (disposable, per-thread, never the audit trail).
- **`dashboard/server/copilot-runtime.js`** (Node, ~30 lines) — the one non-Python piece. `@copilotkit/react-core`'s hooks talk to a CopilotKit Runtime over its own protocol via `runtimeUrl`; they cannot point at a raw AG-UI endpoint directly. This server does nothing but register the FastAPI backend's `/agent` endpoint as a single `@ag-ui/client` `HttpAgent` and re-expose it — no LLM adapter, no chat model, no business logic. Every real decision still happens in the Python graph.
- **`dashboard/`** (React + Vite + Tailwind + shadcn/ui + React Flow + CopilotKit) — the product shell.

## 4. Real bugs found in the CopilotKit/AG-UI stack, and the actual fixes

This phase hit five distinct, reproducible third-party bugs/mismatches across the CopilotKit + `ag-ui` package set (versions in use: `ag-ui-langgraph==0.0.43`, Python `copilotkit==0.1.95`, `@copilotkit/react-core`/`@copilotkit/runtime==1.69.2`). Each is left as a comment at its fix site; summarized here for the next session:

1. **`copilotkit.LangGraphAGUIAgent.clone()` — Python.** Its base class (`ag_ui_langgraph.LangGraphAgent`) evolved new `__init__` kwargs (`enable_legacy_on_interrupt_event`, `emit_interrupt_outcome`, `emit_raw_events`) that `clone()` passes through unconditionally; the CopilotKit subclass never overrode `clone()` to match its narrower `__init__`, so any request hit `TypeError` inside `clone()`. `api/main.py` uses `ag_ui_langgraph.LangGraphAgent` directly instead — it doesn't need CopilotKit's extra layer, and the base class's `clone()`/`__init__` pair is self-consistent.
2. **Express route double-mounting — Node, hit twice (once per Copilot runtime API generation tried).** Both `createCopilotExpressHandler` (v2) and `copilotRuntimeNodeExpressEndpoint` (v1-compat, itself built on the same v2 single-route Hono app internally) reconstruct the full request URL from the *already-mount-stripped* `req.url` and match it against their own `basePath`/`endpoint` option. Mounting either one under `app.use('/copilotkit', handler)` double-prefixes and 404s every request. Fix: mount at root (`app.use(handler)`), letting the handler's own internal path matching do the work — `dashboard/server/copilot-runtime.js`.
3. **`useCoAgent().run()` drops `this`.** In this release, `useCoAgent`'s return object sets `run: agent.runAgent` — extracting the method as a bare reference. Calling it throws inside `@ag-ui/client`'s `HttpAgent.runAgent` (`this.abortController = ...` with `this` undefined): `Cannot set properties of undefined (setting 'abortController')`, reproduced live via an injected `window.onerror` listener (the browser tool's own console/network reads were serving stale/cached results mid-debugging, so a fresh listener installed per-attempt was the reliable way to get a real stack trace). Fix: obtain the same shared agent instance via `useAgent({agentId})` (`@copilotkit/react-core/v2` — not re-exported from the root path, only used internally there) and call `agent.runAgent()` directly as a normal, correctly-bound method call.
4. **`useCoAgent`'s `initialState` never reaches the first request.** The seeding mechanism runs via an `onRunInitialized` subscriber that's supposed to feed back into the outgoing request body, but `useCoAgent`'s own subscriber only calls `agent.setState(...)` as a side effect — it doesn't *return* `{state}` for the aggregation step that actually patches the request. The request is built from `agent.state` *before* `onInitialize()` runs, so the seeded `case_path` silently never arrived — confirmed live via a backend `KeyError: 'case_path'` crash (which then took down the whole Node process, since the resulting mid-stream error wasn't handled gracefully by the fetch layer). Fix: call `agent.setState({...})` synchronously immediately before `agent.runAgent()` in the click handler, rather than relying on `initialState`.
5. **Mixing `@copilotkit/react-core` (root) and its `/v2` subpath crashed React itself.** `useAgent` (v2) internally calls `useCopilotChatConfiguration()` → `React.useContext(...)`, which threw `Cannot read properties of null (reading 'useContext')` — the classic "more than one copy of React" failure mode, caused by Vite's dependency optimizer pre-bundling the root and `/v2` entry points as separate graphs even though they share internal chunks. Fix: `vite.config.ts`'s `optimizeDeps.include: ['@copilotkit/react-core', '@copilotkit/react-core/v2']` forces one consistent pre-bundle pass.

Given (3) and (4), `useCoAgentStateRender`/`useCopilotAction('*')` (CLAUDE.md's named hooks for the live feed) were tried and only ever fired for runs started through `useCoAgent`'s own broken `run()` — never for one started via `agent.runAgent()` directly. `CaseReview.tsx` uses `agent.subscribe({onStepStartedEvent, onStepFinishedEvent, onToolCallStartEvent, onToolCallArgsEvent, onToolCallEndEvent})` instead — the same underlying AG-UI client both of those hooks are built on, typed and documented, with none of the gap. `useCoAgent` is still used for reactive `state`/`running` (that part works correctly). This is a hook-*name* deviation from CLAUDE.md's literal text, not a philosophy one: still headless, still driving a custom case-review UI, never a chat widget.

## 5. What's actually in the UI

- **Case queue** (`CaseQueue.tsx`) — `/cases`, labeled by scenario.
- **Case review** (`CaseReview.tsx`) — a "Run review" button seeds state and calls `agent.runAgent()`; three views update live from the same subscription:
  - **Pipeline graph** (`PipelineGraph.tsx`, React Flow) — nodes/edges from `/graph`, fixed layout (the shape is small and stable — dispatch fans out to four specialists, joining at `escalate_check`, optionally looping through `bump_round`), colored by live status (pending/active/done) from step events.
  - **Step feed** (`StepFeed.tsx`) — chronological node start/finish rows interleaved with live tool-call cards (thinking → executing → complete, arguments rendered as they build).
  - **Results panel** (`ResultsPanel.tsx`) — dispatch plan + reasoning, findings grouped by agent, observations, escalation round badge — all reading straight off `useCoAgent`'s `state`.

## 8. Visual design pass + two more real reliability bugs

A follow-up pass ("make the UI good, easy to use for a supervisor") added: a shared `lib/node-meta.tsx`/`lib/scenario-meta.tsx` (icon + color per agent/node and per scenario label, one source of truth instead of three copy-pasted label maps), a distinct indigo accent theme (`index.css`) instead of shadcn's default neutral-only palette, icon-fronted node cards in `PipelineGraph.tsx`, a redesigned `CaseQueue.tsx` (severity accent bar, per-scenario icon), panel headers with live-pulse indicators in `CaseReview.tsx`, and an auto-scrolling `StepFeed.tsx` (a "live" feed that doesn't follow new events isn't actually watchable).

Testing that pass surfaced two more real, reproducible bugs — one in each half of the stack:

**Frontend — a node could get stuck showing "active" forever.** Traced (via a raw `/agent` curl trace) to LangGraph's default per-node retry policy: a transient failure retries the whole node, re-emitting `STEP_STARTED`/`STEP_FINISHED` for the same `stepName`, and that pair doesn't always survive three hops of SSE relaying (FastAPI → Node CopilotKit runtime → browser) intact on every retry. Rather than chase perfect event delivery, `CaseReview.tsx` now derives the *displayed* node status fresh on every render (`displayNodeStatus`, a `useMemo` over `feed.nodeStatus` and `running`): once the run itself is no longer running, nothing can still be legitimately active, full stop. Correctness no longer depends on every event arriving.

**Backend — a single malformed LLM tool-call element crashed the entire stack.** The actual root cause behind the above: `agents/kya_reasoning.py`'s `record_observations` tool call (`tool_choice: "auto"`, not forced — Anthropic's thinking modes require that) returned one `observations` array element that wasn't a proper `{note, cited_field}` object. The unguarded `o["note"]` inside a list comprehension raised `TypeError: string indices must be integers, not 'str'`, which crashed the LangGraph node → the FastAPI SSE stream → and, since nothing there closes the stream gracefully, the Node CopilotKit runtime's fetch client threw an *unhandled promise rejection* that took the entire Node process down (confirmed in its log: `SocketError: other side closed` after reading 2.7MB). Every case review after that got `ERR_CONNECTION_REFUSED` until the process was manually restarted. Fixed at both ends:
- `agents/llm.py::parse_observations()` — a shared helper (now used by `kya_reasoning.py`, `log_reasoning.py`, `drift_reasoning.py`, which all had the identical list-comprehension-over-an-LLM-array pattern) that skips and logs a malformed element instead of crashing the node. Covered by `tests/test_llm.py`, including a test reproducing the exact live failure shape (a bare string among otherwise well-formed elements).
- `dashboard/server/copilot-runtime.js` — `process.on('unhandledRejection'/'uncaughtException')` handlers so a dropped upstream connection degrades to a failed run in the UI, not a dead server.

Not fixed (flagged, not chased, to stay in scope): an Explore-agent sweep for the same "unguarded LLM tool-output indexing" pattern found lower-risk analogues — single-object field access (not a list comprehension, so one bad response only breaks that one case, not every element in an array) in `log_reasoning.py`'s three verdict checks, `drift_reasoning.py`'s drift verdict, `kya_reasoning.py::narrate_findings`, and `mandate_reasoning.py::check_cart_reasoning_matches_intent`. `pipeline/dispatch.py` already uses the safer pattern (`DispatchPlan.model_validate(result)`, a typed `pydantic.ValidationError` instead of an opaque `TypeError`/`KeyError`) — worth converting the others to that pattern in a future pass, but none of these are confirmed to have fired live the way the Tier-1 array case did.

A layout bug also surfaced below the `lg:` breakpoint: the mobile/stacked grid used the same `flex-1`/`min-h-0` sizing as the desktop two-column layout, but two stacked cards' own `minmax()` floors summed to more height than was available, and the findings card visibly overlapped the live-activity card above it. Fixed by giving cards below `lg:` fixed heights inside a scrolling container instead of forcing everything to fit a viewport that's too short for it; the `lg:` dashboard layout (no page scroll, each card scrolls internally) is unchanged.

## 9. Second design pass: skills, case submission, pipeline-as-hero, and a real duplicate-finding bug

Installed and actually read three third-party skills (`.claude/skills/`, via `npx skills add`) rather than guessing: `frontend-design` (Anthropic), `shadcn` (shadcn/ui team), and CopilotKit's AG-UI bundle (`copilotkit-agui`, `runtime`, `react-core`, etc.). `runtime/references/wiring-langgraph.md` confirmed the Node runtime's `HttpAgent` + `CopilotRuntime` wiring from §3/§4 above matches the officially documented self-hosted pattern, not just a reverse-engineered one. `shadcn`'s own CLI (`npx shadcn@latest info --json`) confirmed this project's real config (`base: radix`, `style: new-york`, `iconLibrary: lucide`) before adding `dialog`, `field`, `input`, `alert`, `empty`, `spinner`, `sonner` for the case-submission flow below.

**Visual identity, following `frontend-design`'s brainstorm-a-real-point-of-view process instead of defaulting to generic SaaS indigo/Inter.** Grounded in the actual subject — a bank regulator's audit console, not a consumer app — the palette became an "ink + paper + brass seal" regulatory-terminal system (`index.css`): a brass/ochre `--primary` (the "official stamp" association) replacing the earlier indigo, paired with Space Grotesk for headings (`font-heading`, a distinctive geometric sans with real character, not another cream-serif-terracotta default) and IBM Plex Mono for data/IDs, loaded via Google Fonts in `index.html`. Status colors (amber=active, emerald=done, red=flagged) deliberately stayed close to their conventional hues — that's signal a case officer relies on, not a place to spend the brief's one aesthetic risk.

**Pipeline made the hero, per direct feedback that it "wasn't visible."** `PipelineGraph.tsx`'s nodes grew substantially — bigger icon roundels tinted by each agent's own brand color even at rest (not just generic gray), bigger type, a status caption ("Waiting"/"Working…"/"Complete"), a corner check/pulse badge — and the layout spacing in `POSITIONS` widened to match. `CaseReview.tsx`'s layout was restructured around it: Pipeline is now a full-width row on its own (`lg:flex-[3]`) with Live Activity and Findings sharing a narrower row beneath (`lg:flex-[2]`, side by side), instead of the previous equal three-way split.

**Case submission — "how is a user supposed to use this, he can't upload a new case."** A real gap: the queue only ever showed the seven synthetic corpus cases. Added a full submission path:
- `data/uploads.py` (new) — validates an uploaded bundle against the exact same `CaseBundle` schema ingestion enforces, persists it to `data/uploads/<case_id>.json`, and returns a manifest-shaped entry so `api/main.py`'s existing `/cases`/`/cases/{id}` endpoints merge corpus + uploaded cases with one code path (`_all_case_entries()`) — no special-casing anywhere downstream, including the pipeline itself, which just sees another `case_path` on disk. New `POST /cases/upload` endpoint (multipart).
- Reuses `data/loader.py`'s QA-note stripping (renamed `strip_qa_notes`, now public) before validating — without it, the dialog's own suggested workflow ("open any case in the queue and use its data as a template") failed live: every real sample file carries internal `_*_note` QA fields at defect locations that `extra="forbid"` rejects outright, which a genuine submission was never going to have anyway.
- Duplicate detection checks both the corpus manifest *and* prior uploads (a first pass only checked uploads, so re-submitting an existing corpus case_id would have silently shadowed it rather than being rejected — caught before shipping, covered in `tests/test_uploads.py`).
- `UploadCaseDialog.tsx` (new) — file picker, inline validation error display (Pydantic's own multi-line message, which is genuinely actionable for someone used to reading rejected forms), success toast (`sonner`), and auto-navigates straight into the new case's review screen.
- A case with no `label` (a real submission has no eval-only ground truth — that's the point of reviewing it) shows a neutral "awaiting review" badge (`scenario-meta.tsx`'s `UNREVIEWED_META`) instead of a scenario badge.
- Covered by `tests/test_uploads.py` (10 tests) and verified live end-to-end in-browser: uploaded a modified sample, watched it auto-open, ran a full live review, findings matched.

**A real data-integrity bug, caught by React's own duplicate-key warning during that live verification.** Running the uploaded synthetic-identity case surfaced two `Finding`s sharing one `finding_id` — not a rendering bug, a real duplicate in `state.findings`. Root cause: the same LangGraph node-retry behavior noted in §8 (confirmed via a raw trace showing repeated `STEP_STARTED`/`STEP_FINISHED` pairs) — a retried node recomputes its deterministic findings from scratch via the same sequential `_FindingIdCounter` (`ingestion/verify.py`, `agents/kya_checks.py`), reproducing identical ids, and `pipeline/state.py`'s `findings`/`observations` channels used plain `operator.add`, which has no way to know a retry's output is a repeat rather something new. Fixed at the actual right layer — the state reducer, not a one-off filter — with `_add_findings`/`_add_observations` (dedup by `finding_id` for `Finding`; by the full field tuple for `Observation`, which has no id of its own), covered by new `tests/test_state.py`. This is also the correct invariant to establish *before* PLAN item 15's hash-chained append-only ledger builds on top of this exact accumulation pattern — an idempotent merge now means the ledger doesn't inherit a double-counting bug later.
