## Specificity verdict: **Specific**

The strongest surfaces could not be worn by another product: the Case file dossier is composed around the AP2 object model itself (signed human sentence → scope/credential evidence pair → Intent→Cart→Payment triptych → numbered delegation ladder), the review gate is a domain artifact (named sign-off, rerun directives aimed at named specialists, in-line round cap), and the logo-derived color system is executed end-to-end — navy-leaning grays, tinted shadows, agent identity hues surviving from sidebar to graph to finding chips via one source. What holds it below Distinctive: the Overview is a marketing-page shape any fintech could wear, the queue is a standard card grid, and the nominated centerpiece — the pipeline graph — renders at rest as an illegible generic flowchart, precisely where a stranger would judge it.

## Priority issues

1. **P0 — The case queue is mouse-only.** `CaseQueue.tsx:78` — cards are `<Card onClick>` divs: no tabindex, no role, no key handling. Measured live: the queue page exposes exactly two focusable elements. The product's primary work surface cannot be operated by keyboard, while the Overview's equivalent rows are proper `<button>`s. **Fixed looks like**: each card a button (or containing one that covers it), visible focus ring, Enter/Space opens.

2. **P1 — The human gate arrives below the fold with no attention direction.** `CaseReview.tsx:289` — at 1440×900 the gate region starts ~1001px down. The one moment the whole system waits on a human is invisible unless the officer thinks to scroll; the only above-fold evidence is a *disabled* button reading "Awaiting decision." **Fixed**: scroll the gate into view on arrival (container-scoped) plus a persistent above-fold affordance — e.g. the header button becomes an enabled "Review decision ↓" anchor.

3. **P1 — The pipeline centerpiece is illegible and interaction-dead at rest.** `PipelineGraph.tsx:17-30, 176-190` — fit-view clamps at minZoom 0.4 → titles 6.4px, captions 4.8px effective (A, measured; corroborated by B's 32× sub-12px census); `zoomOnScroll={false}` + default `preventScrolling` makes the wheel do nothing across a full-width 440px band; no Controls, so a pan or accidental double-click zoom has no way back. **Fixed**: compact the layout (two ranks, narrower nodes) so fit lands ≥0.65 zoom; add zoom/fit controls; `preventScrolling={false}`.

4. **P1 — CopilotKit's `cpk-web-inspector` ships in the product.** Confirmed live: 62×62px floating bubble, fixed top-right, z-index 2147483646, in the tab order, overlapping the header date — despite `showDevConsole={false}` (`main.tsx:14`). Foreign dev-tool chrome on the branded console, against the project's own "never demo from a dev tool" stance. **Fixed**: strip the inspector element in the build; verify the header date is readable again.

5. **P1 — No confirmation, no receipt, at the two irreversible moments.** "Run review" on a case with visible results destroys them instantly (`CaseReview.tsx:189-201`); "Approve & issue" issues on one click with the gate restating nothing about what's being issued, and completion is a meta-string ("issued ✓") — while a mere JSON upload earns a success toast. Peak-end rule violated at the end. **Fixed**: confirm re-run when results exist; gate card summarizes score/tier/finding count above the buttons; issuing produces an explicit success moment naming what was issued.

## Persona red flags (busy bank supervisor, not a developer)

- Live activity streams snake_case tool names and raw JSON blobs as "reasoning on the record."
- Officer-facing node names are pipeline internals: "Ingest", "Bump round", "Escalate check", "Grounding check."
- Case summaries speak in corpus-author voice ("Also the false-positive control.") — eval-speak on the officer's queue.
- The gate demands the officer retype their name every time; weak provenance at the moment of maximal gravity — in a product whose thesis is Ed25519 on everything.
- Untranslated identifiers throughout: `config v3`, `payment_initiation:facilities_procurement`, MCC codes with no lookup.
- The queue has no lifecycle — nothing ever leaves "awaiting review"; a worklist that never shrinks.
- Upload guidance assumes JSON fluency and points to a template affordance that doesn't exist.

## Minor observations

- Always-green "ready" dots on bench and sidebar roster are hardcoded decoration — the exact pattern `AppSidebar.tsx:31`'s own comment disavows; title-only status is inaccessible.
- Amber pulls triple duty (working, flagged scenario, "review" tier) while DESIGN.md reserves red for "flagged."
- `StepFeed.tsx:76` — `scrollIntoView({block:'end'})` scrolls *all* ancestors: during a live run each event drags the page scroller down to the feed, fighting the officer's position.
- `ReportPanel.tsx:72` — the `report_blocked` branch returns before `DecisionTrail`, so prior rerun decisions vanish if a later draft is blocked.
- ScoreCard bars normalize to the max factor (a trivially small top factor renders full-width); headline score set in Archivo though DESIGN.md mandates mono for numbers.
- `STATUS_CAPTION`: "Waiting" (pending) vs "Awaiting reviewer" (gate) — near-synonyms for opposite states.
- Sidebar queue-count badge fetched once on App mount; stale after uploads.
- "What the human authorised" is an uppercase eyebrow above the dossier's de-facto lead heading.
- Empty-state rule met only by StepFeed; ResultsPanel and ReportPanel empties are passive.
- "Next up" implies a priority ordering that is just `listCases()` order.
- Rerun target chips have no `aria-pressed`; selected state is color-only.
- No routing at all: refresh returns to Overview; cases and tabs aren't shareable.
